# Agent Note: Task 前的需求文档

Status: implemented

[English](2026-09-06-requirement-document-before-tasks.md) | 中文

## Problem

“需求”Notebook 需要在实现 Task 出现之前，形成一份可明确审核的目标定义。把原始输入直接渲染成最终需求会丢失澄清结论；使用通用 Plan 模式，则会让实现审批代替需求确认。Task 执行还需要一个确定的本轮验证时机，以及独立判断检查点能否继续推进序列的机制。

## Decision

[集中需求审核决策](2026-09-16-batched-requirement-review.zh.md)替代本说明中的逐 Task 审核频率和“全部运行”停止时机。[本轮验证决策](../simplification/2026-09-24-validate-round-without-final-test.zh.md)替代其中强制生成 Final Test 的规则。本说明继续负责需求文档修订、任务生成、编辑和已记录任务列表的重放。

`startRound` 保留原始需求，并在不进入 Plan 模式的情况下排入歧义分析轮次。主 Agent 首先以只读方式检查仓库。只有仓库无法确定、且会显著影响结果的选择才调用 `clarify_requirements`；每批提出 1 至 5 个相关中文问题，批次数不超过配置上限。问题和答案结算后继续折叠保留在 Notebook 中。如果达到上限后仍有关键歧义，Agent 会让本轮等待用户输入，而不会自行猜测。

Agent 通过 `submit_requirements_document` 提交完整中文需求文档。文档包含 `# 需求文档`、`## 简介` 和 `## 需求`，不包含术语表。每项编号需求包含用户故事和编号验收标准。轮次使用一条不超过 30 个中文字符的独立只读摘要作为标题。执行前可以编辑文档正文。每次编辑都会追加一个经过验证的修订；无效修订保持可见，但不能生成 Task。

用户从需求文档块启动任务生成。`generateTasks` 把一次模型请求绑定到一个确切的有效文档修订，并在请求结算前锁定文档。`submit_requirement_tasks` 为每个顶层阶段创建一个可执行块，同时把对应 `N.x` 勾选项保留在该块内。所有项目都是必做项，并通过 `_关联需求：…_` 引用真实验收标准。生成的 Task 各自验证自身范围，合计覆盖全部验收标准。已记录列表若包含 Final Test，该任务仍可重放和执行。

编辑文档会使当前可见的生成任务列表失效。本轮只要有任意 Task 开始执行，文档就会永久锁定。执行前，用户可以新增、编辑、重排或撤回待处理 Task。执行过程中，已完成、执行中和审核中的 Task 保持锁定；当前 Task 与审核结算且按序执行停止后，才能修改后续待处理 Task。已记录的 Final Test 保持可编辑，但不能移动或撤回。

每个成功的 Task 轮次都必须先经过独立审核，才能变成已完成。审核者返回匹配的 Task 标识，以及 `passed`、`warning` 或 `blocking` 判定。`passed` 和 `warning` 允许按序执行继续。`blocking`、审核不可用或输出无效，以及确认的历史需求回归，都会使 Task 失败并停止“全部运行”。`stopRunAll` 记录停止请求，并在当前 Task 及其审核结算后生效。

所有有效 Task 成功结算后，独立只读审核者依附最后结算的 Task 审核本轮。匹配且非阻塞、无回归的判定会追加本轮验证。已记录的 Final Test 仍遵守原有的末位执行约束，包括不得删除测试、放宽断言或隐藏失败。

[需求 Notebook 流程说明](2026-09-02-requirement-notebook-pipeline.zh.md)继续负责稳定 Notebook 标识、持久 note、Task 单元格呈现和基于证据的历史回归样式。本说明取代其中从 Plan 派生需求与 Task 的创建路径。

## Alternatives considered

**保留 Plan 模式和 Plan 审批。** 予以放弃，因为用户需要审核澄清后的需求文档，而不是审批同时充当需求定义的实现 Plan。通用 Plan 模式在“需求”Notebook 之外继续可用。

**固定询问一组问题。** 予以放弃，因为仓库事实和没有歧义的请求不需要用户输入。问题仅限影响结果且必须由用户决定的选择；依赖前一批答案的歧义可以使用有界的第二批问题。

**每个子勾选项创建一个 Task 块。** 予以放弃，因为用户需要把相关实现和验证步骤放在同一个阶段级执行单元格中。子项继续在一个顶层 Task 块内编辑。

**Task 完成后不经独立审核直接继续。** 予以放弃，因为实现 Agent 的最终回复不是独立证据。审核判定控制 Task 终态和按序续跑。

**把已记录的 Final Test 作为可删除的普通 Task。** 原先强制设置末位任务的决策拒绝此项，因为该任务承担覆盖全部验收标准的最终综合检查。已记录列表仍保留该任务的位置和检查；新生成的列表遵守[本轮验证决策](../simplification/2026-09-24-validate-round-without-final-test.zh.md)。

**允许编辑轮次摘要。** 予以放弃，因为摘要是根据已接受文档生成的导航元数据，需求文档才是用户可编辑的来源。

## Consequences

Session 日志可以重建原始需求、澄清决定、已接受的文档修订、任务生成来源修订、编辑、执行、检查点与本轮审核、按序运行状态、已记录的 Final Test 和验证。用户在实现前拥有一个不依赖 Plan 模式的需求审核点。修订和生命周期锁可以防止使用陈旧文档生成任务，也能防止执行后改写需求。按序执行可能因审核者不可用而停止，但未经独立审核时不会记录成功的本轮验证。

## Testing

Session 测试覆盖歧义分析、澄清持久化、中文文档验证、修订锁、任务生成与引用、已记录 Final Test 的重放、Task 编辑、按序停止、阻塞审核、重试和最终验证。Loader 组合测试通过 `cordis.yml` 启动该包，并检查持久轮次和模型可见的无 Plan 分析提示词。客户端 assembly 和 React 测试覆盖澄清记录、只读摘要、文档编辑与失效、任务生成操作、锁定、审核状态和“全部运行”停止。聚焦 TypeScript 构建验证宿主与客户端编译目标。
